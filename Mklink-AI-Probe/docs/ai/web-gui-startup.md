# Web GUI 卡在 18%：MIME 与旧缓存

## 已确认的原因

启动页内联动画最多自行走到 18%，之后由前端主模块推进。停在这里
说明启动模块没有正常继续，不应直接解释成工程初始化进度。

0.1.8 的静态资源路由直接使用 `mimetypes.guess_type()`。
Windows 注册表把 `.js` 错误关联为 `text/plain` 时，服务返回错误
`Content-Type`，浏览器拒绝执行 ES 模块，Vue 不挂载，浏览器会话不建立。
Python 会读取 Windows MIME 注册表，见
[Python 文档](https://docs.python.org/3.13/library/mimetypes.html#mimetypes.init)。

哈希资源使用一年 `immutable` 缓存，错误响应头也可能被缓存。
仅纠正后端 MIME 并不能让已缓存相同 URL 的用户恢复；普通刷新可能仍
卡在 18%，同一服务换新端口则能启动。其他前端异常也可能造成 18%
停滞，排查时仍需核对实际响应和浏览器错误。

## 0.1.9 修复约定

- `mklink/remote/api.py` 对 `.js`、`.mjs`、`.css` 使用确定的 MIME，
  覆盖 `/assets/` 和普通静态文件路由，不修改用户注册表或全局 MIME 表。
- `gui/vite.config.ts` 使用 `assets/mime-v1` 作为构建资源目录。
  Vite 同时更新入口、静态导入、延迟预加载表、CSS、Worker 和按 URL
  加载的脚本，避免仅改 HTML 时遗漏旧路径。
- 继续保持 HTML 不缓存、哈希资源长期缓存。资源目录前缀是响应规则
  的缓存代号，不是每次构建的随机值；内容变化仍交给文件名哈希处理。
  将来若必须作废相同内容的旧响应头，再更新缓存代号和相应回归断言。
- 修改配置后必须重新构建并提交受版本控制的 `gui/dist`，随后端一起
  更新。目录中的文件与 URL 一致，不依赖 FastAPI 对 HTML/JS 动态改写，
  保留 Tauri 对同一套静态文件的打包方式。
- 所有测试、临时服务和候选产物经 `scripts/build_workspace.ps1` 使用
  主工作区 E 盘 `.build`；不提交浏览器缓存、报告或截图。

## 本次验证（2026-08-28）

- 新增 9 个回归用例在修复前失败，修复后通过：不安全的系统 MIME、
  大小写扩展名、两种静态路由，以及包含延迟资源的构建依赖路径。
- 相关 Python 测试 69 项通过；GUI 全量 57 文件、584 项通过；生产
  构建通过。构建仍有既有的大块体积提示，不影响完成。
- 真实 Chromium 浏览器先缓存 33 个旧构建资源，模拟旧错误响应头。
  同端口只修 MIME 后普通刷新仍停在 18%；再切换完整修复并普通刷新，
  无需清缓存即可进入配置页、仪表盘和 SuperWatch。
- 新路径的 CSS、解码 Worker、波形脚本返回 200 和正确 MIME；请求中
  未见旧资源路径或 HTTP 错误。浏览器会话建立，关闭测试页后释放。
- 浏览器验证使用真实 FastAPI 和生产静态文件；故障注入仅作用于隔离
  测试进程，没有更改注册表、连接设备、烧录或操作供电。

这些结果证明 Web 启动与坏缓存恢复，不代表设备数据采集或 Tauri
安装包升级验收。此次未重跑完整 Python 发布门禁，既有符号链接权限
和隔离依赖安装限制仍记录在项目记忆中；没有合并 master 或正式发布。
