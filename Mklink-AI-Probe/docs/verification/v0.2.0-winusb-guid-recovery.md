# Windows DAP 消失：接口 GUID 缺失现场与定点恢复

日期：2026-09-05。用户报告 USB 连接不稳定时，Keil 和上位机同时找不到探针，以前需要卸载 DAPLink 驱动再拔插。用户保留故障现场供检查。

跟踪状态（2026-09-06）：用户要求暂时登记、暂停继续修复。已恢复的接口登记与尚未确定的高速 USB 不稳定触发原因分别保留；不标记为根因已解决。后续获准继续时，从故障枚举阶段证据入手。

## 已证实的直接原因与恢复

1. Windows 的 MKLink V4 复合设备、DAP（MI_00）和三个 CDC 串口均存在，PnP 状态正常。DAP 驱动为 Microsoft `winusb.inf` / `WINUSB`，没有上下层过滤驱动。
2. 当前 DAP 实例 `Device Parameters` 下缺少 `DeviceInterfaceGUIDs`。`pnputil /enum-interfaces` 找不到启用的 CMSIS-DAP GUID 接口；源码 API `/api/online-flash/probes` 返回空数组。正常历史设备实例有该值。
3. 保留注册表和 PnP 记录后，经 Windows UAC 管理员确认，仅给当前 MI_00 添加标准 CMSIS-DAP GUID，并执行一次该接口的 `pnputil /restart-device`。未卸载驱动、未删除父设备、未拔插、未刷探针或目标固件。
4. 重启该接口成功，上位机探针枚举从 0 个恢复为 1 个。随后打开 DAP，仅发送信息查询，得到协议 `2.1.1`、包大小 512、包数 2、能力值 307；测试句柄已关闭。没有向目标发送连接、复位、写内存或烧录命令。
5. 用户强调硬件为高速 USB 后，直接读取设备核实 `usb_speed=3 (High Speed)`，DAP OUT/IN 端点最大包均为 512；实际 BOS 33 字节、MS OS 2.0 集合 170 字节，现场返回的 `DeviceInterfaceGUIDs` 和 GUID 正确。当前并未降为 Full Speed，也没有修改高速模式。

这证明缺少 GUID 是本次“驱动已启动但应用找不到”的直接阻断条件；未证明 GUID 最初为何未持久化。USB 不稳定期间的控制传输中断/不完整安装是与用户触发条件一致的假设，尚无原始枚举阶段 USB 跟踪证据。`ExtPropDescSemaphore=1` 在正常历史实例中也存在，不能单凭该值判定死锁。

接口 GUID 的用途见 [Microsoft WinUSB 自动安装说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/automatic-installation-of-winusb)；CMSIS-DAP GUID 见 [Arm USB 配置说明](https://arm-software.github.io/CMSIS_5/DAP/html/group__DAP__ConfigUSB__gr.html)。

## 固件代码审查

检查了用户提供的 MicroLink Plus 工程 `microlink_app/src/usb_configuration.c`、`usb_configuration.h`、`dap_main.c` 和实际构建引用的 HPM SDK 1.10.0 CherryUSB 栈。保留该工程原有未提交修改，本轮未改写/烧录下载器固件。

- 源码确实上报 `DeviceInterfaceGUIDs`，类型 REG_MULTI_SZ、标准 GUID 和双 NUL 终止均存在。另从本地既有 2026-08-30 ELF 中解析验证：MS OS 2.0 集合 170 字节、功能子集 160 字节、注册表属性 132 字节，BOS 的长度引用一致。**这是源码/既有构建检查，不是当前设备固件回读。**
- `dap_transport_reset()` 已在 USB RESET、DISCONNECTED、CONFIGURED 事件清理队列并在配置完成时重新启动 OUT 接收。不能把“缺少 USB reset 清理”当作本次结论。
- 存在独立的降速兼容缺陷（**并非当前故障已证实的触发条件**）：`config_descriptor_callback(speed)` 忽略速度，Bulk 描述符统一用 `DAP_PACKET_SIZE=512`；Full Speed Bulk 最大包应为 64，High Speed 为 512，参见 [Microsoft USB Bulk 传输说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-bulk-and-interrupt-transfer)。当前实测为 High Speed，512 正确。
- `other_speed_config_descriptor` 使用 `USB_CONFIG_DESCRIPTOR_INIT`，生成类型 2，应该返回类型 7 的另一速率配置；该版本 CherryUSB 栈原样使用回调返回内容，不替固件修正类型或包大小。SDK 已提供 `USB_OTHER_SPEED_CONFIG_DESCRIPTOR_INIT`。
- 下一轮本故障调查应优先捕获高速链路不稳定时的枚举/控制传输及 Windows 接口登记，不能把降速缺陷当作当前根因。HS/FS 描述符、DAP/CDC 包边界与 ZLP 可作为独立兼容修正，并在描述符变化时管理 `bcdDevice` 版本。不能只把 512 改成 64 就宣称修复；必须验证短包边界及反复 USB reset 下的所有复合接口。当前没有不稳定链路复现验收，不能宣称消除复发。

## 可重复使用的修复工具

`scripts/win_dap_interface.ps1` 默认只读自检。需要传入设备管理器“设备实例路径”中的具体 MI_00 路径；拒绝父设备、CDC、其他品牌/驱动、不在场设备以及通配符。

```powershell
./scripts/win_dap_interface.ps1 -InstanceId '<当前 MKLink MI_00 的完整设备实例路径>'
```

确认输出 `MissingDapGuid=true` 后，在管理员 PowerShell 中使用相同实例，加 `-Apply -BackupDirectory '<绝对备份目录>'`。它先导出注册表、保存修复前计划及 `rollback.ps1`，保留其他已有 GUID，只补缺失项并重启该 DAP 接口。GUID 已存在时不写注册表、不重启；驱动错误、不同注册表类型等情况拒绝猜测修复。

验证：PowerShell 实机只读自检、管理员修复、注册表回读、真实枚举和 DAP 信息查询均通过；一个 Python 驱动的 PowerShell 测试覆盖 12 个正确性/拒绝条件。此工具按需运行，不在后台自动修改系统驱动设置。

原始注册表、PnP 输出、修复日志和回滚脚本只存于忽略目录 `.build/reports/usb-guid-20260905`，不提交设备标识或主机私有路径。Keil 界面内重新选择探针及不稳定 USB 条件复测仍需补充；本轮没有安装新驱动或升级固件。
