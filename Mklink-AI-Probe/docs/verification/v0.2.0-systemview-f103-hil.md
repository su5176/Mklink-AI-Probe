# 0.2.0 SystemView 烧录后时基 HIL（2026-09-05）

## 范围与环境

用户授权使用现有 STM32F103 测试工程修改、编译和下载，完成一轮真机测试。
实际目标为 MKLink V4 + STM32F103RE，读取确认 512 KiB Flash、72 MHz；
测试固件采用 RT-Thread、SystemView RTT 通道 1。保留原供电，不执行 VCC
调整、加锁/解锁或探针固件升级。后续用户要求释放串口，由其手动排查 UART。

应用源码只修改构建标识 `2026090302` → `2026090501`，没有修改 SystemView
计时配置或加入寄存器补写。先备份完整 512 KiB Flash、原 main.c、AXF/HEX；
通过 Keil AC6 编译，0 errors / 4 warnings。派生工程、构建输出及日志均在
忽略的 `.build`，验证后的 AXF、HEX、MAP 已同步回用户工程的原输出位置。

通过源码后端的真实 `/api/online-flash` 流程执行两轮相同 HEX 的
connect → 扇区擦除 → program → verify → reset → disconnect，目标普通暂停
连接、1 MHz、default reset。镜像从 `0x08005000` 开始，不覆盖前置 bootloader。
两轮作业均成功，修复后一次约 8.8 秒。本轮不生成或安装桌面包。

## 复现与修复

同步上游 SystemView 会话修复后，现有固件附着采集正常；但第一次 pyOCD 在线
烧录后，`DEMCR=0`、DWT CYCCNT 连续读取固定为 `5501612`。同时新构建标识
可读、应用心跳递增，SystemView 事件数持续增加但时间戳停住，证实目标程序
仍在运行。旧版问题没有被上游的主机会话重试修复关闭。

本机 pyOCD `CortexM.disconnect()` 在普通恢复运行路径清空 DEMCR。
采用其文档支持的 [core disconnect 回调](https://pyocd.io/docs/user_scripts.html#will_stop_debug_core)
实现受限的生命周期修复：

- 仅成功完成普通、非安全操作的 reset/run 后启用状态保留。
- 断开前按核捕获当时的 `TRCENA`；断开清理后仅恢复原本置位的该位并回读校验。
- 不恢复调试器 vector-catch 位，不改 DWT CTRL/CYCCNT，不强制开启原本关闭的跟踪。
- 保留已有 delegate、断点/观察点清理、恢复执行和关闭探针流程；读写失败先允许
  清理完成，再将状态保留失败报告给作业。
- 安全操作、失败复位和没有 reset/run 的路径保持原行为；HPM ROM 路径不变。

相同固件第二轮在线下载后，`DEMCR=0x01000000`、DWT CTRL=`0x40000001`，
CYCCNT 持续递增。没有额外执行 GUI MCU reset，也没有修改目标代码绕过故障。

## 真实浏览器验证

使用当前生产 GUI 和修复后的 Python 源码后端，在真实 Edge 中操作 RTOS Trace。
RTT 地址由当前 AXF 搜索得到，页面显示七个任务与 72 MHz。

| 场景 | 结果 |
| --- | --- |
| 烧录后短采集 | 持续收到有效事件、时间戳前进，停止与资源释放成功 |
| 长流，含暂停显示/继续 | 约 72 秒、最终 590521 events；统计区间墙钟 67.486 s，跟踪时间 67.481 s |
| 同一连接第二次启动 | 约 15 秒、127216 events；统计区间墙钟 10.007 s，跟踪时间 9.994 s |
| 自动恢复 | 两个浏览器会话均为 0 次，没有依靠重试维持长流 |
| 传输/Worker | 收到 2304 个二进制消息、约 34.3 MB，2634 个 Worker 消息 |
| 暂停显示 | 后端事件数继续增加，恢复显示成功 |
| 停止/断开 | stream.active_clients=0，采集停止、设备断连、资源租约为空 |
| 页面 | 零 JavaScript 异常、零 console error |

每个会话的解析器丢弃 11 字节、0 packets；目标 overflow 为 0。该字节数在
采集初始即出现且未增长，不宣称完全无丢弃或所有跟踪内容均已语义验证。
