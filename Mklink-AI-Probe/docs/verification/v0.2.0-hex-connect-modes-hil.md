# 合并 HEX 与在线烧录连接方式回归

日期：2026-09-03。分支：`codex/v0.2.0-development`。

## HEX 故障与修复

用户提供的 GD32F303xE HEX 有两个合法的 05 型启动地址记录，位于第 449、11304 行，分别为 `0x08000131`、`0x08008131`。原有预检查接受它，但实际编程与校验又交给另一解析器，导致先擦除、后报 `Start Address Record appears twice`。

修复后预检查、编程和校验共用严格的数据记录解析。启动地址只是入口元数据，不参与写入地址选择；合法的重复 03/05 记录可以接受，校验和、重叠、EOF、溢出与资源限制仍严格检查。编程将所有独立数据段通过真实 pyOCD `FileProgrammer.add_file` 排队后一次提交，不填平段间空洞，不修改原文件。

原始客户文件的离线执行准备验证：

| 数据范围（右端不含） | 字节数 |
| --- | ---: |
| `0x08000000–0x08001BE4` | 7,140 |
| `0x08008000–0x08032618` | 173,592 |

合计 180,732 字节。真实 FileProgrammer 的暂存结果与校验迭代得到的字节完全相同；提交测试替身不接触硬件。原始客户固件、截图及本机日志不进入 Git，也没有将 GD32 固件写入 STM32。

文件快照在设备连接及擦除前复查。复制期间除文件元数据外还比较源内容哈希，覆盖 Windows/共享文件系统同大小、时间戳不变的内容变化。

## STM32 真机与连接方式

Browser 插件控制实际 WebGUI；MKLink V4、STM32F103RE、1 MHz，使用现有测试工程 HEX。应用数据范围 `0x08005000–0x08020060`，共 110,688 字节，仅擦除覆盖扇区，未擦写低地址已有引导程序；未操作加锁、解锁、VCC 或全片擦除。

修复前，“连接后暂停”在算法 Init 出现 HardFault（IPSR=3），“保持运行”出现首地址读回不符，“复位下连接”加硬件复位通过。只读寄存器诊断表明失败链路的算法准备复位前后 PC 和 CONTROL=2 均未变化，RTOS 的进程栈状态被保留。

原代码只把“硬件复位”用于任务尾部，算法准备仍使用默认软件复位。现在将明确选择的硬件复位传入会话；算法执行前检查异常状态与栈/权限上下文，不合格时在擦除前停止，不自动改成物理复位。任务尾部若目标仍暂停、锁死或处于复位，报告复位失败，并禁止断开时误运行遗留 RAM 算法。

首个下载器的实际对照（末项运行状态检查加入前的成功记录，不作为该新增检查的验收）：

| RST 接线 | 连接方式 | 复位方式 | 观察结果 |
| --- | --- | --- | --- |
| 接入 | 暂停／保持运行／复位下连接 | 硬件 | 三组均完成编程、读回校验和复位 |
| 断开 | 暂停／保持运行 | 默认／软件 | 四组均完成编程、读回校验和复位 |
| 再接入 | 暂停／保持运行 | 默认／软件 | 四组复现上下文未复位，新增保护在擦除前拦截 |

此对照证明接线会影响该下载器与目标组合的软件复位，不能单凭 GPIO 软件配置推断外部电路是推挽或开漏。用户随后更换为已改开漏 RST 的 V3，并确认新版 V4 同样采用开漏 RST；后续以开漏硬件为前提，不为旧 V4 增加专门兼容或复位回退。上述上下文与运行状态检查是所有下载器共用的安全检查。本轮不修改下载器固件。

| 连接方式 | 默认复位 | 软件复位 | 硬件复位 |
| --- | --- | --- | --- |
| 连接后暂停 | 通过 | 通过 | 通过 |
| 保持运行 | 通过 | 通过 | 通过 |
| 复位下连接 | 通过 | 通过 | 通过 |

九个独立 GUI 任务均为 succeeded，耗时约 9.7–11.1 秒。每组包含覆盖扇区擦除、HEX 编程、逐字节读回校验、复位后 RUNNING/SLEEPING 状态检查及断开；未出现解析错误、校验失败或复位失败。此运行状态检查不等同于完整业务功能验收。

随后用户拔掉 V3 的 RST，保持同一测试板及其他接线，补测结果：

四组均从 WebGUI 发起，完成擦除、编程、读回校验、复位运行状态检查和断开。最终下载后，按现有 MAP 中的变量地址，通过公共 CLI `dump-memory` 在同一普通命令会话采集 3 个样本、100ms 间隔：`g_demo_sample_count` 与 `g_mklink_heartbeat` 均为 139→140→141，三帧 flags=0，无解析丢帧/CRC 警告，确认应用主循环继续运行；采集结束停止流并关闭连接。端口发现自动识别替换的 V3，没有复用旧 V4 不存在的命令口。此补测未修改源码、目标固件或供电。

## GD32 客户 HEX 与运行后自动保护

用户换为 GD32F303CET6 并接回 RST。只读检查得到 `DBG_ID=0x21040414`、密度签名 512 KiB Flash / 64 KiB RAM；WebGUI 精确选择 CET6，使用内置 `GD32F30x_HD.FLM`，无需联网下载 Pack。客户文件名标注 VET6，本轮只验证同容量 CET6 的烧录与读回，不以此判定客户的板级外设功能正常。

实际加载客户原始 HEX，两段范围与上文离线检查一致。首次“连接后暂停＋默认复位”完整烧录、180,732 字节校验、复位与断开成功，耗时 13.06 秒，没有重复启动地址解析异常。

固件启动后再次下载，“保持运行＋默认复位”以及“复位下连接＋硬件复位”均返回首地址 `0x08000000` 页编程错误码 1。只读检查保护选项已为 `BB 44`，保护生效时 `FMC_OBSTAT=0x03FFFFFE`、SPC 位为 1，Flash/密度读取失败，而芯片 ID 与选项寄存器仍可读。本地静态分析也确认客户固件把 `0xBB` 传入写选项字节的调用链，最终写入保护区；不是 HEX 中包含选项区数据。用户随后向客户确认，该固件运行后会自动加锁，每次下载都需解锁。保护值写入与影子状态生效有复位时序差异，不能只看其中一个断言当前读保护状态。

用户明确授权永久擦除整片 Flash，以 3.3V 断电复位解锁并回烧，随后授权同一板卡后续每次下载前按此流程解锁。精确型号安全能力返回 supported=true。由于当前 WebGUI 不允许仅解锁任务，独立解锁调用 CLI 的共用安全后端；没有更换算法或绕过白名单。首轮解锁后检查得到 `A5 5A`、SPC 清零、密度签名恢复，公共 dump-memory 按 32 KiB 有界分块读取全部 524,288 字节均为 FF，擦除态 SHA-256 为 `043E238A765F7CFBC62596A50E53C8FFB6B188A99357B0EBEDE251725D67589F`。原有数据已永久清除，只回烧客户 HEX 所覆盖的数据。

解锁后通过 WebGUI 再测原失败的“保持运行＋默认复位”，完整编程、校验、复位及断开成功，耗时 11.92 秒；启动后选项区再次写入 `BB 44`。后续每次先通过共用 CLI 后端解锁、以 3.3V 断电复位，再用 WebGUI 执行所选下载模式，最终矩阵如下（耗时仅包含 GUI 下载任务，不含前置解锁）：

| 连接方式 | 默认复位 | 软件复位 | 硬件复位 |
| --- | --- | --- | --- |
| 连接后暂停 | 通过，13.06 秒 | 通过，11.90 秒 | 通过，12.09 秒 |
| 保持运行 | 通过，11.92 秒 | 通过，11.86 秒 | 通过，12.10 秒 |
| 复位下连接 | 通过，11.95 秒 | 通过，11.92 秒 | 通过，12.12 秒 |

共 9 个成功 GUI 下载任务、8 次成功独立解锁，另保留 2 个未解锁时的失败对照。所有 GUI 任务的原文件 SHA-256 均一致，结束时源文件哈希也未改变。九组均完成两段数据校验及复位运行状态检查，不把保护状态下的失败归因为连接模式缺陷。CLI 在保护连接/断电退出时有 CoreSight 与 board uninit 警告；成功结论依据任务状态、解锁后整片擦空检查和后续真实编程校验，而非忽略警告只看进程退出码。

最终固件已回烧，选项区再次为 `BB 44`，即时影子状态为 `0x03FFFFFC`（SPC 当时尚未重新加载为 1）。这与固件启动后写入保护、在后续复位/重新进入调试时体现保护效果的观察一致；没有再解锁并把芯片留空。所有硬件任务已结束并释放连接。

额外的 WebGUI 单任务“解锁＋擦除＋烧录＋校验＋复位”最初因宿主原生确认框阻塞而未完成验证。随后改为页面内风险确认，同日补测一条 GD32F303CET6 解锁/擦除/烧录/校验/3.3V 断电复位作业成功，用时 15.184 秒。详见 [桌面确认与脱机能力评估](v0.2.0-desktop-confirmation-offline-security.md)；不是脱机脚本解锁验证。
