# GD32F303 普通暂停加解锁复测（2026-09-05）

## 范围与结果

GD32F303CET6、512 KiB Flash / 64 KiB RAM、V3 下载器，用户授权使用 3.3V、永久解锁擦除并恢复客户镜像。本轮连接模式始终选择 halt，不主动选择 under-reset；未测量 RST 引脚波形，不能声称底层错误恢复从未触碰 RST。

- 在线独立解锁成功；独立回读全部 524288 字节均为 FF。
- 在线下载客户 HEX、校验成功；运行前独立回读全部 512 KiB，与 HEX 数据及空隙填 FF 的预期镜像完全一致。
- 在线独立加锁及断电恢复成功，物理保护字节和影子状态相符。
- 同一在线作业 unlock → erase → program → verify → lock 最初出现 `LOCK_FAIL: flash init timed out`。修复算法生命周期后，完整作业含断电恢复成功，约 36.32 秒。
- 脱机自动脚本连续两轮 unlock → HEX 下载 → lock 返回成功；脚本配置 `connect=halt`、`off_ms=3000`、`off_max_mv=800`、3300mV。另用设备侧解锁及 HEX 加载命令在运行/加锁前停住，独立回读全部 512 KiB，与同一预期镜像完全一致。
- Chrome 新页面验证 GD32 器件联想、勾选解锁立即确认、确认后自动切为普通暂停连接，以及 3 秒断电提示。取消测试勾选后保留页面，旧读回数据页面未被刷新覆盖。硬件作业使用同一 WebGUI 后端 API，未冒充全部由鼠标启动。

## 已修复的独立问题

GD32 选项 FLM 的 `uninit()` 只结束当前算法操作，不清除 pyOCD 的已加载标记。解锁后主 Flash 算法覆盖同一目标 RAM，再次加锁会跳过选项 FLM 重载，执行被覆盖的入口。现在选项操作结束使用 `cleanup()`，下次重新装载；回归测试模拟了主算法覆盖 RAM 的情形。

此修复不依赖客户固件自锁，与驱动枚举问题也无关。只修改已验证的 GD32 路径，未扩张其他芯片白名单。当前工作树另含未提交的脱机功能和普通暂停策略修改，不属于本报告对应的独立生命周期修复提交。

## 未闭环：客户程序运行状态

用户再次确认客户固件运行后会自行加锁。因此重新连接后受保护、无法读取主 Flash，不能当成下载失败。

不过，脱机加锁后读到 DHCSR 的 LOCKUP 标志；改用不写 C_DEBUGEN 的 CDC 读取也观察到该状态。额外分步检查发现锁定配置执行后、脚本末尾 `set_reset`/`cpu_run` 之前已出现，不能直接归罪于成功收尾。运行前全 Flash 比对已排除下载内容不一致；地址 0 向量与主 Flash 向量一致。原因尚不能在客户程序、保护下调试交互和启动流程之间唯一归因。

厂商手册说明保护时调试模式下主 Flash 访问受限，修改保护后连接着调试器时需电源复位；这只是分析依据，不是运行成功证明：[GD32F30x 用户手册 §2.3.11](https://www.gd32mcu.com/data/documents/userManual/GD32F30x_User_Manual_Rev2.9.pdf)。

用户将提供不会自行加锁的程序用于对照。已停止硬件操作；最后恢复的是客户原镜像，退出调试后以 3.3V 断电恢复，未再次接入 SWD 检查，不能宣称独立运行已验证。换程序后需重新核对镜像、供电与擦除授权。

## 后续：用户更换的新程序

用户换程序后先读回完整 512 KiB，两次读取一致并单独备份，不覆盖上一份客户 HEX。新程序对应 AXF 的 19296 字节加载段与备份一致；该构建无 RTT 符号，源码输出为 UART/CAN，未宣称 RTT 捕获成功。

在线加锁、解锁后全片空白、恢复比对均成功。V3 脱机从已加锁状态解锁、完整 BIN 下载、加锁成功，BIN 下载约 44.94 秒；再用设备侧解锁/下载并保持暂停，独立全片回读与新备份一致。全程选择普通 halt，3.3V。

最终恢复未加锁并断电启动，三次运行快照都为 RUNNING、线程模式、CFSR=0，PC 位于该 AXF 的 YMODEM/运算代码内。已恢复运行、释放会话，无新固件编译或安装包。加锁后的调试读取仍见 LOCKUP，故不能仅归因于旧客户程序自锁；加锁后无调试独立运行仍未证明，需与恢复后的正常执行分开记录。
